# requirements-plan

## Purpose

SPEC은 "무엇을 만족해야 하는가"만 말한다. 이 단계는 그것을 "이 코드베이스에서 어디를, 어떤 순서로 건드리는가"로 바꾼다.

판단 기준이 앞 단계와 다르다. `requirements-specify`까지는 요구사항 원문만 보면 되지만, 여기서는 실제 코드와 `.claude/rules/`의 컨벤션을 읽어야 한다. 그래서 별도 단계로 둔다.

산출물은 그대로 구현 순서가 되고, 각 작업 항목이 커밋 하나에 대응한다.

## Must Follow

- **코드를 작성하지 않는다.** 계획까지가 범위다. 파일을 미리 만들어 두지도 않는다.
- **추측으로 파일 목록을 만들지 않는다.** 수정 대상은 실제로 찾아서 확인한 파일만 적는다. 신규 파일은 `.claude/rules/architecture/architecture-directory.md`의 배치 규칙에 근거를 두고 경로를 정하며, 그 근거를 계획에 적는다.
- **작업 단위는 커밋 단위다.** `.claude/rules/git/git-commit.md`를 따른다. 하나의 논리적 변경만 담고, 각 단위는 그 자체로 빌드가 깨지지 않아야 한다.
- **모든 SPEC이 최소 1개의 작업에 매핑된다.** 어느 작업에도 속하지 않는 SPEC이 남으면 계획이 덜 된 것이다.
- **테스트는 선별한다.** `.claude/rules/test/test-convention.md`의 "무엇을 테스트하는가" 표를 따른다. 전부 테스트하겠다고 적지 않고, 테스트하지 않는 것과 그 이유도 함께 적는다.
- **완료 조건을 관찰 가능하게 적는다.** "제대로 동작한다"가 아니라 "무엇을 보면 끝났다고 판단하는지"를 적는다.
- **애매하면 질문한다.** 배치나 분해 방식이 두 갈래로 갈리면 임의로 고르지 않고 선택지를 제시한다.
- **미확인 항목이 남아 있으면 먼저 처리한다.** `02-spec.md`에 미확인 항목이 있으면 계획을 세우기 전에 사용자에게 확인받는다.

## Input

- `_workspace/<branch>/02-spec.md`
- `.claude/rules/` — 배치, 계층, 컴포넌트, 테스트 컨벤션
- 실제 코드베이스

## Workflow

1. **`02-spec.md`를 읽는다.** 미확인 항목이 남아 있으면 여기서 멈추고 확인받는다.
2. **관련 규칙 문서를 읽는다.** 최소한 아래는 확인한다.
   - `.claude/rules/architecture/architecture-directory.md` — 파일을 어디에 둘지
   - `.claude/rules/architecture/architecture-ipc.md` — main/renderer 경계를 넘는 동작이 있을 때
   - `.claude/rules/architecture/architecture-state.md` — 상태를 어디에 둘지
   - `.claude/rules/ui/ui-component.md` — 화면을 만들 때 컴포넌트를 어떻게 나눌지
   - `.claude/rules/test/test-convention.md` — 무엇을 테스트할지
3. **코드베이스를 탐색해 영향 범위를 확정한다.** 수정할 파일은 실제로 열어 확인하고, 신규 파일은 배치 규칙에 따라 경로를 정한다.
4. **작업을 커밋 단위로 나누고 순서를 정한다.** 앞 단위가 뒤 단위 없이도 빌드되는지 확인한다. 순서가 강제되는 의존이 있으면 그 이유를 적는다.
5. **각 작업에 대응 SPEC ID와 완료 조건을 붙인다.**
6. **테스트 계획을 세운다.** 어떤 SPEC을 어떤 테스트로 검증할지 연결하고, 테스트하지 않는 영역과 이유를 적는다.
7. **커버리지를 확인한다.** SPEC별로 어느 작업에 반영됐는지 역방향으로 채운다.
8. **계획을 사용자에게 보여주고 확인받는다.**

## Output

`_workspace/<branch>/03-plan.md` (`templates/plan.template.md` 템플릿 참조)

## Done When

- 모든 SPEC이 최소 1개 작업에 매핑됐고, 커버리지 표에 빈 행이 없다.
- 각 작업이 커밋 하나로 끝나는 크기이며, 그 자체로 빌드가 깨지지 않는다.
- 신규 파일 경로마다 배치 근거가 적혀 있다.
- 각 작업에 관찰 가능한 완료 조건이 있다.
- 테스트 계획에 "테스트하지 않는 것과 이유"가 포함되어 있다.
- 코드는 한 줄도 작성하지 않았다.
- 사용자가 계획을 확인했다.

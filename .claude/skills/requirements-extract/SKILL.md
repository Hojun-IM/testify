# requirements-extract

## Purpose

사용자의 정제되지 않고 추상적인 요청에 포함되지 않은 숨은 결정사항을 사용자와의 대화로 하나씩 표면화하고 확정한 뒤, 확정된 내용을 원자적이고 명확한 요구사항 문장으로 정리한다.
대화를 통한 발견과 결과물 정리를 순차적으로 수행하며 이 단계의 산출물이 곧 다음 단계(`requirements-specify`)가 EARS 패턴으로 정책화할 최종 요구사항 목록이다.

## Must Follow

- **절대(NEVER) 사용자 대신 결정하지 않는다.** 그럴듯한 기본값이라도 확인 없이 확정하지 않는다. 에러 케이스, 엣지 케이스, 제약조건 등 그럴듯해 보이는 내용이라도 사용자가 직접 답하지 않았다면 적지 않는다.
- **티켓은 대화의 대체물이 아니라 시드다.** 티켓이 존재한다는 것과 티켓이 충분하다는 것은 다르다. 티켓으로 채워진 결정 지점만 질문에서 제외하고, 나머지는 평소대로 대화한다. 티켓이 있다는 이유로 대화를 건너뛰지 않는다.
- **티켓에 없는 내용을 티켓에서 온 것처럼 적지 않는다.** 각 요구사항에 출처(티켓/대화)를 표시하고, 티켓 문장을 확대 해석하지 않는다.
- **여러 턴에 걸쳐 대화한다.** 초기 요청이 막연할수록 한 번에 물어볼 질문 목록 자체를 만들 수 없다. 주제 하나씩 순차적으로 다루며 답변에 따라 다음 질문을 조정한다.
- **선택지를 제시한다.** 백지 질문("검증은 어떻게 할까요?")보다 구체적 선택지("가입 시점에 검증할지, 저장 직전에 검증할지, 둘 다 할지")를 제시해야 사용자가 빠르게 답할 수 있다.
- **이미 언급된 내용은 다시 묻지 않는다.** 사용자가 이미 답을 준 부분, 티켓에 명시된 부분을 재확인하느라 대화를 늘리지 않는다.
- **한 번에 1~2개 주제만 다룬다.** 결정 지점을 한꺼번에 나열하면 사용자가 대충 답하게 된다.
- **정리 단계에서는 원자적 문장으로 재작성한다.** 하나의 요구사항에는 조건 하나, 결과 하나만 담는다. "A이고 B이면 C이고 D한다"처럼 복합적인 문장은 "A이고 B이면 C한다" / "A이고 B이면 D한다"로 쪼갠다.
- **미해결 항목은 미해결로 남긴다.** 질문했는데 답을 받지 못했다면 요구사항 목록에 편입시키지 않고 "미확인" 목록에 남긴다. 다음 단계로 임의로 넘기지 않는다.
- **구현 세부사항을 확정하지 않는다.** 상태 코드, 정확한 필드명, 에러 포맷 같은 기술적 실현 방식은 requirements-specify의 몫이다. 사용자가 먼저 명시하지 않았다면 "인증되지 않은 사용자는 접근할 수 없다"처럼 행동 수준으로만 적는다. "401을 반환한다"처럼 구현 값을 직접 적지 않는다.

## Input

다음 중 하나로 시작한다.

- **노션 티켓 ID 또는 URL** (예: `TICKET-123`, `https://notion.so/...`) — 티켓을 조회해 결정 지점을 채운 뒤 남은 부분을 대화로 확정한다.
- **자유 형식 요청** — 한 문장짜리 아이디어부터 몇 문단짜리 설명까지 무엇이든 가능하다.
- **이미 정리된 요구사항 문서** — 결정 지점이 모두 채워져 있음이 확인되면 대화 없이 정리 단계(6~8번)만 수행한다. 빈 곳이 있으면 티켓과 동일하게 취급한다.

## Workflow

1. **티켓을 조회한다.** (티켓 입력이 없으면 건너뛴다.)
   - URL이 주어지면 `notion-fetch`로 바로 가져온다.
   - 티켓 ID만 주어지면 `notion-search`로 찾는다. 결과가 여러 개거나 확신이 서지 않으면 후보를 보여주고 사용자에게 확인받는다. **추측으로 고르지 않는다.**
   - 찾지 못하면 진행하지 않고 URL을 요청한다.
   - 가져온 티켓의 제목과 링크를 기록해 둔다. 원문 전체를 산출물에 복사하지 않는다.
2. **작업 브랜치를 준비한다.** (티켓 ID가 있을 때만.)
   - `.claude/rules/git/git-branch.md`에 따라 `develop`에서 `feature/<티켓 ID>` 또는 `fix/<티켓 ID>`를 만든다.
   - `feature`인지 `fix`인지는 티켓 성격으로 판단하고, 애매하면 사용자에게 묻는다.
   - 해당 브랜치가 이미 있으면 체크아웃만 한다.
   - 티켓이 없으면 브랜치를 만들지 않고 현재 브랜치명을 출력 경로에 쓴다.
3. **결정 지점을 식별한다.** 이 기능/변경에서 보통 결정이 필요한 영역을 떠올린다. 입출력 형태, 검증 시점과 방식, 예외/실패 처리, 권한 범위, 성능·규모 가정 등. 기능 성격에 따라 관련 없는 영역은 건너뛴다. (`checklists/requirements-extract.checklist.md`에 자주 등장하는 영역을 확인한다. 기계적으로 전부 물어보라는 뜻이 아니라 놓치기 쉬운 영역을 점검하는 용도로 참고한다.)
4. **티켓 내용으로 채울 수 있는 결정 지점을 먼저 채운다.** 티켓에 명확히 적힌 항목은 출처를 `티켓`으로 표시하고 질문 목록에서 뺀다. 티켓 문장이 애매하면 채운 것으로 간주하지 말고 질문 대상으로 남긴다.
5. **남은 결정 지점을 주제별로 묶어 순차적으로 질문한다.** 관련된 결정끼리 묶고, 한 번에 1~2개 주제씩 선택지 형태로 제시한다. 답변이 다른 결정에 영향을 주면(예: "리스트 응답"을 선택하면 페이지네이션 여부도 정해야 함) 그 자리에서 후속 질문을 추가한다.
6. **핵심 동작이 구체화되면 요약해서 확인받는다.** 모든 디테일을 다 캐물을 필요는 없다. 이후 단계(구현)에서 판단 가능한 영역까지 여기서 확정할 필요는 없다.
7. **확정된 내용을 원자적 문장으로 재작성한다.** 조건 하나, 결과 하나만 담도록 쪼개고, 목적/배경, 대상/트리거, 제약조건, 제외 대상을 구분해 정리한다. 각 항목에 출처(`티켓` / `대화`)를 표시한다.
8. **미해결 항목을 별도로 표시한다.** 질문했지만 답을 못 받은 부분은 요구사항 목록에 넣지 않고 "미확인" 항목으로 명시적으로 남긴다.

## Output

`_workspace/<branch>/01-requirements.md` (`templates/requirements.template.md` 템플릿 참조)

`<branch>`는 현재 체크아웃된 브랜치명을 그대로 쓴다 (예: `_workspace/feature/TICKET-123/01-requirements.md`).

## Done When

- 모든 요구사항 문장이 원자적이다 (한 문장에 조건 하나, 결과 하나).
- 기능의 핵심 동작 방식이 사용자 확인을 거쳐 확정됐다.
- 임의로 채워넣은 가정이 없다. 확정된 내용은 전부 사용자가 직접 답했거나 티켓에 명시된 것이다.
- 각 요구사항에 출처가 표시되어 있다.
- 모호했던 지점은 전부 질문했고, 답변받은 것은 반영, 못 받은 것은 "미확인"에 명시적으로 남아있다.
- 티켓 입력이었다면 작업 브랜치가 준비되어 있다.
- 사용자가 "이제 됐다, 진행해도 된다"고 확인했다.

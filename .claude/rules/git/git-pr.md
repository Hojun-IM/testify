# Git PR 규칙

PR은 "어떤 작업이고, 무엇을 했고, 무엇이 어떻게 바뀌었는지"를 리뷰어가 코드를 열어보기 전에 파악할 수 있어야 한다. `git-branch.md`, `git-commit.md`와 동일하게 티켓 ID를 기준으로 일관성 있게 작성한다.

## PR 시점

- `feature/*`, `fix/*` 브랜치 작업이 끝나면 `develop`으로 머지하기 위해 PR을 생성한다.
- 빠른 개발이 목표이므로 PR 리뷰 자체는 필수로 강제하지 않는다 (`git-branch.md` 참고). 다만 PR을 생성하는 경우 아래 규칙을 따른다.
- 하나의 PR은 하나의 티켓에 대응한다. 여러 티켓 작업을 한 PR에 섞지 않는다.

## PR 제목

```
<type>(<티켓 ID>): <제목>
```

- `<type>`, `<제목>` 규칙은 `git-commit.md`의 커밋 메시지 규칙을 따른다.
- 제목만 보고 "어떤 작업인지" 파악할 수 있어야 한다.
- 예: `feat(TICKET-123): 로그인 폼 유효성 검사 추가`

## PR 본문 템플릿

```markdown
## 작업 배경 / 목적
- 왜 이 작업이 필요했는지 (티켓 링크 또는 티켓 ID 명시)

## 변경 사항
- 무엇을 했는지 (기능/파일 단위로 나열)
- 변경 전/후 동작 차이가 있다면 명시

## 테스트
- 어떻게 확인했는지 (재현 절차, 실행 명령, 스크린샷 등)

## 참고 사항
- 리뷰어가 알아야 할 특이사항, 후속 작업, 제약사항 (없으면 생략)
```

- "변경 사항"은 커밋 목록을 그대로 나열하지 말고, 리뷰어 입장에서 변경 단위를 요약한다.
- UI 변경이 있으면 스크린샷/GIF를 첨부한다.
- 티켓 ID는 본문에 최소 한 번 이상 명시해 추적 가능하게 한다.

## 원칙

- 제목과 본문만 읽고도 코드를 열어보기 전에 변경 범위를 예측할 수 있어야 한다.
- 리뷰어가 맥락을 찾으러 티켓/슬랙 등을 오가지 않도록, 필요한 배경은 PR 본문에 요약해서 담는다.
- PR 크기는 리뷰 가능한 수준으로 유지한다. 너무 커지면 티켓 단위로 쪼갤 수 있는지 먼저 검토한다.

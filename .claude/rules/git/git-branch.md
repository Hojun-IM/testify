# Git 브랜치 전략

빠른 개발 속도를 우선하는 단순화된 Git Flow를 사용한다. 릴리즈 브랜치, hotfix 브랜치 등 무거운 규칙은 두지 않는다.

## 브랜치 구성

- `main`
  - 항상 배포 가능한 상태를 유지한다.
  - 직접 커밋하지 않고 `develop`에서 머지로만 갱신한다.
- `develop`
  - 기본 통합 브랜치. 평소 작업은 이 브랜치를 기준으로 분기한다.
  - 완료된 feature/fix 브랜치를 이 브랜치로 머지한다.
- `feature/*`, `fix/*`
  - `develop`에서 분기해 작업 단위(기능/버그 수정)로 짧게 유지한다.
  - 작업이 끝나면 `develop`으로 머지 후 삭제한다.

## 네이밍 규칙

- 티켓 ID를 기반으로 브랜치명을 생성한다.
- `feature/<티켓 ID>` (예: `feature/TICKET-123`)
- `fix/<티켓 ID>` (예: `fix/TICKET-456`)
- 티켓이 없는 작업은 브랜치를 생성하지 않는다.

## 작업 흐름

1. `develop`에서 `feature/*` 또는 `fix/*` 브랜치를 생성한다.
2. 작업 브랜치에서 커밋하며 개발한다.
3. 작업이 끝나면 `develop`으로 머지하고 브랜치를 삭제한다.
4. 배포 시점에 `develop`을 `main`으로 머지한다.

## 원칙

- 브랜치 수명은 최대한 짧게 유지한다 (며칠 이내).
- `main`은 항상 배포 가능해야 하므로 검증되지 않은 변경을 직접 올리지 않는다.
- 빠른 개발이 목표이므로 PR 리뷰나 릴리즈 브랜치 같은 절차는 필수로 강제하지 않는다. 필요할 때만 선택적으로 사용한다.

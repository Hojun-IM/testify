# Git 커밋 규칙

커밋 단위와 메시지는 한눈에 보고 내용을 파악할 수 있어야 하고, 모든 커밋이 동일한 형식을 따라 일관성을 유지해야 한다.

## 커밋 단위

- 커밋 하나에는 하나의 논리적 변경만 담는다 (예: "로그인 API 연동" 과 "버튼 스타일 수정"을 한 커밋에 섞지 않는다).
- 서로 관련 없는 변경(포맷팅, 리팩토링, 오타 수정 등)은 별도 커밋으로 분리한다.
- 커밋만 보고도 "무엇을 왜 바꿨는지" 파악되지 않으면 단위가 너무 크거나 섞여 있는 것이다. 이 경우 커밋을 나눈다.
- 반대로 지나치게 잘게 쪼개서(예: 저장할 때마다 커밋) 히스토리를 읽기 어렵게 만들지 않는다. 하나의 완결된 작업 단위로 묶는다.
- 빌드가 깨지는 상태의 커밋은 만들지 않는다. 각 커밋은 그 자체로 정상 동작해야 한다.

## 커밋 메시지 형식

[Conventional Commits](https://www.conventionalcommits.org/) 형식을 따른다.

```
<type>(<티켓 ID>): <제목>

<본문 (선택)>
```

- `<type>`: 변경 성격을 나타낸다.
  - `feat`: 기능 추가
  - `fix`: 버그 수정
  - `refactor`: 동작 변화 없는 코드 구조 개선
  - `style`: 포맷팅, 세미콜론 등 코드 의미에 영향 없는 변경
  - `docs`: 문서 변경
  - `test`: 테스트 추가/수정
  - `chore`: 빌드, 설정, 의존성 등 기타 작업
- `<티켓 ID>`: 작업 중인 브랜치의 티켓 ID를 그대로 사용한다 (예: `TICKET-123`). `git-branch.md` 참고.
- `<제목>`: 무엇을 했는지 명령형으로 간결하게 작성한다 (예: "로그인 폼 유효성 검사 추가"). 끝에 마침표를 붙이지 않는다.
- `<본문>`: 제목만으로 배경/이유가 설명되지 않을 때만 작성한다. "무엇을"이 아니라 "왜"를 적는다.

예시:

```
feat(TICKET-123): 로그인 폼 유효성 검사 추가

feat(TICKET-123): 로그인 실패 시 에러 메시지 표시

fix(TICKET-456): 창 종료 시 크래시 발생하는 문제 수정

빈 세션 상태에서 close 이벤트가 두 번 호출되어 발생한 문제.
```

## 원칙

- 제목은 50자 내외로 짧게, 본문이 필요하면 한 줄 띄우고 작성한다.
- 커밋 메시지에 "수정", "업데이트" 같은 모호한 표현만 쓰지 않는다. 무엇을 수정/업데이트했는지 제목에 드러낸다.
- 하나의 티켓 안에서도 여러 커밋으로 나눌 수 있다. 다만 각 커밋은 위 형식과 단위 원칙을 지킨다.
